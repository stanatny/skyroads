# Nebula Cruise Rhythm and World Polish Design

**Date:** 2026-08-03

**Status:** Approved

**Delivery target:** Update the open `feat/stellar-command-polish` pull request against `main`

## 1. Context

The current command-center polish is technically complete, but playtest feedback identifies three experience gaps:

1. the adaptive soundtrack has an appropriate cinematic electronic timbre but feels too relaxed for the game speed;
2. procedural drones, turrets, buildings, barriers, and gaps do not match the finish of the rendered player ship;
3. the yellow mission button is visually abrupt, while existing restart shortcuts are undiscoverable.

The approved direction is a focused second polish pass inside the existing pull request. It preserves gameplay rules and the current adaptive, offline-first architecture while replacing the weak presentation layers.

## 2. Goals

- Make normal play feel joyful, propulsive, and slightly tense within the first two seconds of a run.
- Preserve the current cinematic electronic sound palette and synchronized three-stem adaptive playback.
- Give drones, enemy turrets, low barriers, high buildings, and gap edges one coherent, high-quality sci-fi art direction.
- Make world art respect lane position, depth, and the road's perspective instead of behaving like flat screen stickers.
- Preserve the drone's readable `warn -> move` direction telegraph.
- Replace the yellow mission action with the approved deep-blue-to-violet treatment.
- Expose the existing `Enter` / `Space` start-and-restart shortcuts and `Escape` return shortcut in the interface.
- Keep browser, GitHub Pages, and packaged `file://` macOS behavior aligned.
- Deliver a real gameplay screenshot, a playable build, and a user-listenable music candidate before final acceptance.

## 3. Non-goals

- No new enemy behavior, combat rule, collision size, spawn probability, difficulty curve, score rule, leaderboard behavior, or persistence schema.
- No runtime WebGL renderer, runtime 3D model loading, or remote asset dependency.
- Fuel and the BOOST, SLOW, TRIPLE, and MAGNET rewards remain readable animated Canvas symbols. They receive only material/glow harmonization, not model replacement.
- Pause and the wider V1.1 release contract remain separate planned work.
- The repository game-delivery Skill remains separate planned work.

## 4. Approved Experience Direction

The pass uses the following combined direction:

- **Music:** retain cinematic synthwave instrumentation, rewrite the content at 128 BPM, and introduce a clear pulse during normal play.
- **World art:** use CC0 Quaternius and KayKit 3D source assets, render them offline into local multi-view transparent sprite atlases, and retain the current procedural art as per-object fallback.
- **Mission actions:** use the selected deep-space blue to violet gradient for `Start Mission` / `开始任务` and `Fly Again` / `再来一局`.
- **Shortcuts:** show `Enter / Space` on both mission actions and `Esc` on the game-over return action.

## 5. Rhythm-forward Adaptive Music

### 5.1 Musical contract

The replacement score remains an original deterministic render generated by `tools/generate-music.js` from the committed score document.

- Tempo: **128 BPM**.
- Meter and length: **4/4, 32 bars, exactly 60 seconds**.
- Render contract: stereo 16-bit PCM source renders at 44.1 kHz, exactly **2,646,000 frames per stem**.
- Tonal center: E minor, with brighter Dorian/relative-major turns so the loop feels forward-looking rather than gloomy.
- Loop: the first and final edges retain the existing short safety fade, with no audible seam across two complete loops.

The three synchronized stems have distinct responsibilities:

1. `atmosphere` keeps the cinematic pads, space texture, and short identifying motif. Pad attacks and releases are shortened so they do not blur the pulse.
2. `drive` carries the normal-play groove from the first bar: syncopated bass, defined kick, backbeat, and an eighth-note high-frequency pattern with restrained sixteenth-note pickups.
3. `overdrive` adds sixteenth-note arpeggiation, denser percussion, and a tension counter-line. It is audible at low level during normal play and becomes prominent at high speed, low fuel, or BOOST.

The first audition candidate uses these exact playback targets:

| State | Atmosphere | Drive | Overdrive | Low-pass cutoff |
|---|---:|---:|---:|---:|
| Menu / game over | 1.00 | 0.00 | 0.00 | 4.2 kHz |
| Normal play | 0.72 | 0.92 | 0.18 | 8 kHz |
| Speed ratio >= 0.75, danger, or BOOST | 0.68 | 1.00 | 0.78 | 14 kHz |

All gain and filter changes retain the existing 300 ms ramp. The first candidate normalizes atmosphere, drive, and overdrive to respective peaks of `0.68`, `0.72`, and `0.66`, and sets the music-bus gain to `0.55`. An automated offline sum of the intense mix must remain at or below `0.95` peak. If the user requests an arrangement revision after audition, the final exact normalization and bus values are re-measured, written into the score/runtime contract, and locked by the same headroom test.

### 5.2 Playback and fallback

The existing playback architecture remains:

1. a user gesture unlocks audio;
2. one complete supported format is chosen for all three stems;
3. the three decoded buffers start at the same `AudioContext` time and share identical loop boundaries;
4. OGG remains primary and MP3 remains compatibility fallback;
5. the 138 BPM procedural chiptune remains the last-resort fallback when neither complete stem set is usable.

Audio failure never blocks gameplay. Music and SFX mute preferences retain their current separate local persistence.

### 5.3 Audition gate

The first rendered candidate is not treated as final merely because technical tests pass. The user receives:

- directly playable candidate audio;
- a playable game build demonstrating normal and intense mixes;
- an opportunity to request one tuning revision before final binaries and hashes are accepted.

Final listening checks cover laptop speakers and headphones for two complete loops, plus a five-minute gameplay session. Acceptance requires a clear pulse within two seconds, an unmistakable but smooth intense-state lift, audible SFX, and no clipping, pumping, drift, click, or loop seam.

## 6. Licensed World-art System

### 6.1 Sources and visual language

The approved source families are:

- Quaternius, **Sci-Fi Essentials Kit**: <https://quaternius.com/packs/scifiessentialskit.html>
- KayKit, **Space Base Bits**: <https://kaylousberg.itch.io/space-base-bits>

Both official pages identify their free assets as CC0. This pass uses only files from the free editions. Runtime code never hotlinks either site.

The offline render treatment is shared across every selected source:

- deep navy armor and structural surfaces;
- violet or magenta hostile energy seams;
- cool cyan environmental rim light that matches the command-center world;
- red hostile identification, muzzle, and warning lights;
- restrained bloom that does not enlarge the apparent collision core;
- transparent padding with zero RGB under fully transparent pixels.

### 6.2 Replacement scope

The pass replaces the presentation of every hostile building or trap category while preserving its current gameplay identity:

| Gameplay category | New presentation | Preserved behavior |
|---|---|---|
| Drone | Two cosmetic hostile drone/robot variants | Height, hitbox, bob, warning, lane movement, kill behavior |
| Enemy turret | Two cosmetic base-and-weapon variants | Height, hitbox, player tracking, warning light, kill behavior |
| Low wall | Two low barricade / energy-gate variants | Jumpable height, lane footprint, destruction rules |
| High wall | Two tower / heavy-structure variants | Non-jumpable height, lane footprint, destruction rules |
| Gap | Modeled deck-edge and hazard-frame treatment around the projected opening | Exact support test, safe jump height, bridge and full-gap generation |

Fuel and the four reward pickups remain programmatic symbols so they remain recognizable at speed and are never confused with hazards. Their gradients, metal rims, and glow colors are harmonized with the new world art without changing silhouettes.

### 6.3 Offline outputs

Downloaded source models are not committed. The repository commits only the actual runtime atlases, official license copies, render tooling, and provenance needed to reproduce and audit the outputs; the provenance document records direct official download locations plus exact upstream filenames and hashes.

Each upright or airborne cosmetic variant uses its own local transparent PNG atlas with seven horizontal yaw frames centered around the road camera. The yaw set is `-30, -20, -10, 0, 10, 20, 30` degrees. Each frame is 512x512 and uses the same camera pitch, light rig, ground anchor, and output canvas. Keeping one variant per atlas makes loading, fallback, provenance, and tests independent.

Expected runtime outputs live under `assets/world/` and cover:

- two drone variants;
- two turret variants with separately drawable weapon/telegraph layers where required;
- two low-barrier variants;
- two high-structure variants;
- one gap-edge / hazard-frame atlas.

`tools/render-world-assets.swift` owns the deterministic offline render recipe. `docs/assets/world-art.md` records the renderer hash, exact upstream filenames and hashes, output hashes, camera, lighting, palette treatment, atlas layout, and reproduction command.

## 7. Perspective-correct Runtime Rendering

### 7.1 Multi-view selection

A new small pure module, `src/world-art.js`, owns world-art metadata and view selection. It does not own gameplay rules.

For every upright asset:

1. gameplay supplies the existing continuous world lane position and segment depth;
2. the renderer computes the viewing azimuth from the camera to the asset using its projected world X and `zRel`;
3. the azimuth is clamped to the atlas range;
4. the two neighboring yaw frames and a blend factor are selected;
5. the frames are bottom-center anchored at `project(worldX, 0, zMid)` and scaled from the existing world width and height;
6. neighboring frames cross-fade linearly across their 10-degree interval using the fractional view angle, avoiding a visible view pop while keeping both frames on the same bottom-center anchor.

This makes a structure reveal the appropriate side when it sits in a left or right lane and lets that angle converge toward the center as distance increases. Depth remains governed by the existing perspective projection rather than arbitrary CSS or screen-space scaling.

Shadows, warning zones, projectile origins, barrel aim, and collision-debug geometry continue to be generated in world space and projected independently. A sprite's transparent wings, glow, antennae, or barrel do not redefine the lethal footprint.

### 7.2 Ground traps

Gaps are not drawn as upright sprites. Their opening continues to use the four projected lane/segment corners, guaranteeing exact agreement with the road perspective and collision support test. New source-derived deck edges, damaged panels, lights, and hazard markings are placed along those projected boundaries. The void, embers, and depth interior remain procedural so bridge runs and full-width gaps can stretch without texture distortion.

### 7.3 Drone movement telegraph

The existing state and timings remain authoritative:

- `rest` keeps the selected visual lane;
- `warn` lasts 0.6 seconds without moving the collision lane;
- `move` interpolates the same continuous lane value for rendering, projectiles, and collision over 0.4 seconds.

The new art makes direction readable with three redundant cues:

1. the drone banks toward its destination;
2. a red/magenta chevron points toward the target lane;
3. a projected landing marker appears on the destination lane during `warn`.

During `move`, the sprite view is selected from the same continuous position returned by `enemyLane()`. No sprite-only motion is allowed. Under reduced motion, bob, rapid blink, and cosmetic rotor animation freeze, but the bank angle, direction chevron, and static landing marker remain visible.

## 8. Asset Loading and Failure Handling

The visual asset manifest gains a `world` group. Preloading remains bounded and non-blocking.

- Player ship frames remain required for the preferred player rendering path.
- Every world atlas is optional independently.
- A missing or undecodable atlas falls back only that category or variant to the existing procedural renderer.
- A partial world-art failure must not discard successfully loaded categories.
- The diagnostic snapshot reports loaded and fallback world-art categories without changing the existing meaning of the player-ship fallback field.
- The macOS package continues to copy the complete `assets/` tree and the resource smoke continues to compare it recursively.

Runtime HTML, CSS, and JavaScript retain zero remote URL dependencies.

## 9. Mission Actions and Shortcut Discoverability

### 9.1 Visual treatment

`Start Mission` / `开始任务` and `Fly Again` / `再来一局` receive a dedicated `mission-action` modifier instead of sharing the old yellow styling with unrelated dialog actions.

The approved normal-state palette is:

- background: `linear-gradient(110deg, #203e94, #5845b7)`;
- border: `#7797ff`;
- text: `#f5f8ff`;
- restrained internal blue-violet glow;
- cyan focus outline with adequate separation from the button border.

Hover, active, disabled, and focus-visible states keep text contrast and do not reintroduce a solid yellow fill. Gold remains available for scores and other established semantic highlights. Rename/save and other dialog actions use the existing dark-glass/cyan hierarchy rather than the mission gradient. The opaque yellow button frame becomes unused and is removed from runtime assets, asset tests, and its selected-file entry in the provenance record.

### 9.2 Shortcut presentation

The current keyboard behavior remains the source of truth:

- `Enter` or `Space` starts from the command center;
- `Enter` or `Space` starts a new run from game over;
- `Escape` returns from game over to the command center.

Both mission buttons display a compact `Enter / Space` keycap hint and set `aria-keyshortcuts="Enter Space"`. The game-over return action displays an `Esc` hint and sets `aria-keyshortcuts="Escape"`. Chinese and English catalogs include the explanatory text, while physical key labels remain locale-independent. On coarse-pointer viewports narrower than 640 CSS pixels, the visual keycaps are hidden to preserve action space, while the accessible metadata remains.

Repeated keydown, focused text input, and open modal behavior retain their current guards so a shortcut cannot accidentally start a run while the player edits a name or views a dialog.

## 10. Component Boundaries and Data Flow

The focused file structure is:

```text
assets/audio/source/nebula-cruise-score.json   deterministic musical contract
assets/audio/                                  synchronized OGG/MP3 stems
assets/world/                                  local multi-view runtime atlases
src/audio.js                                   adaptive loading and state mix
src/world-art.js                               atlas metadata and pure view selection
src/presentation.js                            preloading, buttons, shortcut metadata
src/game.js                                    gameplay state and projected drawing integration
styles/game.css                                mission action and shortcut keycap styling
tools/generate-music.js                        deterministic score renderer
tools/render-world-assets.swift                deterministic multi-view renderer
docs/assets/audio-generation.md                audio reproduction and validation
docs/assets/world-art.md                       source, license, render, and hash record
THIRD_PARTY_NOTICES.md                         shipped third-party provenance
```

Frame data flows in one direction:

```text
game state -> continuous world position / enemy state
           -> pure view selection + projected anchor
           -> loaded atlas frame or category fallback
           -> Canvas draw
```

World art never mutates generation, movement, collision, shooting, scoring, or persistence state.

## 11. Verification

### 11.1 Automated checks

Implementation follows red-green TDD and extends the existing suite with:

- exact 128 BPM / 60-second / 2,646,000-frame score assertions;
- deterministic render equality and synchronized stem-duration checks;
- onset/pulse and headroom guardrails that prevent a sustained pad from dominating normal play again;
- normal and intense mix/cutoff transition assertions;
- atlas file, dimensions, alpha padding, frame-layout, and output-hash assertions;
- authoritative source URL, license-copy, upstream filename, upstream hash, and modification-record assertions;
- pure view-selection tests across center, left, right, near, far, and continuous drone movement;
- renderer/fallback tests for every hostile building and trap category;
- warning-direction tests covering left, right, static reduced-motion, and the existing 0.6/0.4-second state contract;
- unchanged collision-boundary, height, safe-lane, spawn, and destruction assertions;
- DOM tests for mission-only styling, translated visible hints, `aria-keyshortcuts`, focus, modal guards, and repeat suppression;
- complete resource and WKWebView smoke coverage for local audio and world atlases.

The complete `npm test`, `npm run check`, macOS resource, architecture, signature, and WKWebView smoke suites must pass before completion.

### 11.2 Manual checks

Manual browser and packaged-app checks cover 960x600, 1280x800, 1440x900, and 1920x1080 in Chinese and English.

Acceptance requires:

- hostile silhouettes remain recognizable at maximum speed and render distance;
- left/right lane perspective and near/far view transitions do not pop or ghost materially;
- drone direction is readable before it moves;
- visible clearance agrees with collision behavior;
- gaps, low walls, high walls, drones, and turrets share one art language;
- reduced-motion mode retains static hazard and direction information;
- mission buttons are prominent without the previous yellow interruption;
- keyboard, pointer, touch, and modal focus behavior remain correct;
- the packaged app decodes music and loads every preferred/fallback world path locally.

## 12. Delivery and User Gates

Changes land as additional commits on `feat/stellar-command-polish`, automatically updating the existing pull request. The branch is not merged by the implementation process.

Before final handoff, the user receives:

1. directly playable candidate music and an in-game dynamic-mix preview;
2. a real 1280x800 gameplay screenshot captured from the running build with a drone and hostile structure visible at speed;
3. the playable local URL for hands-on review;
4. source/license documentation and current verification results.

Music binaries and visual acceptance are finalized only after this review. Production GitHub Pages is verified only after the user merges the pull request and the deployment points at the merged `main` commit.
